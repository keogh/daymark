## Safety and isolation preflight

For every environment:

- [ ] Use a disposable OS user, VM, or physical test profile that cannot resolve
  to the developer's real `Daymark` application-data directory.
- [ ] Record the isolation method without a personal username or full private path.
- [ ] Obtain the installer and `SHA256SUMS.txt` from this repository's own draft
  GitHub Release page, not from a workflow workspace or third party.
- [ ] Verify the exact artifact checksum before installation.
- [ ] Keep normal platform security enabled. Never disable Gatekeeper,
  SmartScreen, antivirus, or machine-wide execution policy.
- [ ] Launch Daymark as the disposable ordinary desktop user. Linux package
  installation/removal may request normal administrator authorization, but the
  application itself must never run with `sudo`.
- [ ] Do not manually delete the profile during replacement, uninstall, or
  reinstall checks.
- [ ] Do not attempt a downgrade or open a newer profile with an older Daymark
  version; downgrade compatibility is unsupported.

## Bounded acceptance procedure

Perform this sequence separately in every required environment.

### 1. Fresh install and normal launch

1. Confirm the clean disposable test user has no Daymark profile.
2. Download the matching artifact and manifest from the recorded draft Release.
3. Verify SHA-256, then install through the platform flow below.
4. Launch from Finder/Launchpad, Start menu, or the GNOME launcher without a
   source checkout or Node.js installed.
5. Confirm the Daymark launcher/task-switcher or dock icon and the separate
   platform-appropriate tray/menu-bar icon.
6. Confirm the platform-appropriate per-user profile is owned by the ordinary
   user and user data is not inside the application or installer directory.
7. Confirm a second normal launch leaves only one reachable Daymark instance.

### 2. Online smoke and lifecycle

Create the synthetic fixture. Confirm close hides without stopping tracking, tray
restore and pause/resume work, switching and stop work, History and Analytics show
the fixture, settings survive restart, and explicit Quit/relaunch reconstructs the
running timer. Observe renderer console and application/main-process logs. Any
unexpected error, missing local asset, second instance, or profile ownership issue
is blocking. Do not copy Task content or private paths into evidence.

### 3. Offline smoke

1. Disconnect networking with the normal OS UI or VM control.
2. Relaunch and repeat representative start, close/restore, tray pause/resume,
   switch, stop, History, Analytics, Settings, Quit, and relaunch checks.
3. Use an OS/VM network inspector to confirm Daymark makes no HTTP(S) request.
   Record the method and result, not unrelated traffic.
4. Reconnect only after offline checks pass.

### 4. Same-candidate replacement or reinstall

1. Leave the fixture intact with Task A running or paused and record the state.
2. Quit normally without stopping or mutating the timer solely for installation.
3. Replace/reinstall the same candidate through the supported platform flow.
4. Relaunch as the same ordinary user and confirm the same Tasks, intervals,
   History, Analytics, settings, and reconstructed Timer state remain.
5. Confirm migrations complete without error and the profile was not relocated or
   recreated.

### 5. Uninstall and reinstall

1. Quit Daymark and uninstall through the platform flow below.
2. Confirm installer-owned binaries, entries, and installed icons are removed.
3. Confirm the per-user profile, SQLite database, and settings remain. Uninstall
   intentionally preserves personal data; manual profile deletion is a separate
   destructive action outside SPEC-011.
4. Reinstall the same verified candidate as the same user and confirm the complete
   fixture and reconstructed Timer state remain.

### 6. Forward upgrade policy

For this first release, record `Not applicable — no immediately preceding
published Daymark artifact exists`; do not simulate an upgrade with a changed
version or untracked build.

Starting with the second release, this is mandatory on every platform family:
install the immediately preceding published, checksum-verified artifact, create
the synthetic fixture, quit with a running or paused timer, upgrade through the
supported flow, and confirm the candidate opens the same profile with successful
migrations, complete data, settings, projections, and reconstructed Timer state.
Never open the upgraded profile with the earlier application.

## Platform-specific instructions

### macOS

Open the matching DMG and install through Finder. If Gatekeeper blocks the unsigned,
unnotarized app, first confirm origin and checksum, try to open Daymark once, then
open **System Settings > Privacy & Security**, choose **Open Anyway** for Daymark,
and confirm the prompt. Do not disable Gatekeeper globally. Replace through the
same Finder flow. To uninstall, quit and remove the installed Daymark application;
do not remove the profile.

### Windows 11 x64

Run `Daymark-0.1.0-win32-x64 Setup.exe` as the ordinary user. Installation is
per-user and must not require an administrator account. If SmartScreen warns,
confirm origin and checksum, choose **More info**, inspect the application and
publisher details, then intentionally choose **Run anyway**. Do not disable
SmartScreen or antivirus. Use the same Setup executable for replacement. Uninstall
through **Settings > Apps > Installed apps**; do not remove the profile.

### Ubuntu GNOME x64

Install the DEB with standard package tooling and normal administrator
authorization. Launch **Daymark** from GNOME as the ordinary desktop user; never
run Daymark with `sudo`. Confirm the per-user profile is owned by that user. Use
the same package flow for replacement. Remove the package without purging or
manually deleting the profile, then confirm `/usr/bin/daymark`, the desktop entry,
installed application files, and installed icon are gone while the profile remains.
